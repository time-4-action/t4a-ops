Plan at a glance

Phase 0 cannot wait. After it, each phase builds on the one before: the Slack app from Phase 1 carries the maintenance command, that command announces the migration windows, and Phase 5 moves the databases once the apps sit on Hetzner.

Estimates assume agentic work: Claude writes the code, runs the tests and makes the server changes; you review pull requests and approve each switch. Your review time and the maintenance windows set the pace, not typing.

Phase 1: Slack alerts and daily summary

One Slack channel tells you every morning that all is fine, and tells you at once when something breaks. Done 2026-10-25.

  • Slack app "t4a server" posting into #t4a-server
  • Backup scripts post to Slack on failure, and a daily summary at 06:00 CET: every backup with time and size (red when older than 26 h, so a backup that never ran shows too), the Postgres restore window, disk, RAM and containers on both servers
  • Backup heartbeat URLs in /etc/t4a-heartbeat.env, so a server that is down entirely also alerts (Phase 2)
  • Documented in t4a-infra servers/alerts/README.md

Phase 3: Maintenance from Slack

A slash command in Slack puts a banner in every app, or a maintenance page in front of chosen sites. Effort: about 1 day, including the banner in every app. Built before the migration so the moves can be announced with it.

Apps only read banner.json, so a new app joins by adding the banner component; down mode bypasses the apps entirely.

Phase 4: Move everything off T-2

Everything in the T-2 table moves to Hetzner or is retired, so the T-2 server can be cancelled. Hetzner has room: T-2 uses about 2.4 GB of RAM and 13 GB of data, Hetzner has about 5 GB of RAM and 60 GB of disk free. Effort: 2 to 3 days of agent work, spread over 3 short maintenance windows. Each step keeps the T-2 copy stopped but intact for two weeks.

  1. Preparation, no downtime
    • Check whether MetaKocka, PNV, POINT-7 or Unifiber only accept T-2's IP
    • Cloudflare origin certificates in Traefik for time-4-action.com, patrik-international.com and the-chase-project.com
    • MongoDB 8 container on Hetzner (internal network only) and a MariaDB container for WordPress
    • Per repo, a PR with Traefik labels, no ports on 0.0.0.0, deploy paths and deploy secrets (deploy secrets need an org admin)
  2. Stateless and small, no window: export portal UI, mk-automation, the patrik-international.com proxy, the mail autodiscover server, time-4-action.com website files
  3. Window 1, MongoDB apps: stop on T-2, copy all three MongoDB databases (about 20 MB), start on Hetzner: portal API, partners API, admin, chat, warranty form. Chat drops host networking
  4. Window 2, Recharge Hub: stop web, worker and Postgres; pg_dump from 16, restore into the shared 18; copy .env with ENCRYPTION_KEY; check one inventory sync and the app in Shopify admin
  5. Window 3, WordPress: patrik-web and the-chase-project with PHP-FPM in Docker, MariaDB dump and restore (130 MB), 5.3 GB of site files copied ahead and synced again in the window
  6. Monitoring: Uptime Kuma and Beszel move to Hetzner, plus one free outside check that watches them
  7. Retire: archive then delete patrik API, products, UI and t4a-sync folders, Prometheus, Grafana, mail-migration and patrik-test; n8n and mcp per your decision
  8. Cancel the T-2 server after two quiet weeks. Mail runs on T-2's mail servers (MX mx1.t-2.si), which looks like a separate T-2 product; confirm with T-2 that cancelling the server leaves mail alone

Phase 5: Everything on Postgres

Every app ends on the shared Postgres and MongoDB is switched off; WordPress is the one exception, it only runs on MySQL or MariaDB. About 2 weeks of agent work in total, measured from each repo's code; the export portal API and t4a-admin are most of it. Each app moves on its own, never in the same step as a server move.

How the portal moves safely:

  1. Admin, chat and mcp leave the t4a database first, so the portal is its only owner
  2. All MongoDB calls in the portal go behind one data-access module, still on MongoDB, released and tested on its own
  3. Postgres implementation behind that module: products and feed payloads as jsonb with indexes on the fields queries use, the 9 aggregations rewritten as SQL
  4. A copy script moves the data; exports from both databases are compared before the switch
  5. Switch in a maintenance window announced from Slack; MongoDB stays read-only for two weeks as the rollback
  • Sizes measured from the repos on 2026-10-25; re-check before each app starts
  • Phase 5 starts after the migration in Phase 4
  • When the last app is off: switch MongoDB off and drop it from the backups
